# Phase 2 isolated procedure fixture plan

Prepared 2026-09-30. No procedure fixture has run.

The deployed procedure and its Snowpark modules use fully qualified `QUAKEWATCH.RAW` and `QUAKEWATCH.CURATED` table names. Running a synthetic update or deletion through that procedure would write fixture records into the real project tables. The earlier temporary-table check exercised only the checked-in current-view SELECT, so it cannot establish procedure-level update or tombstone behavior.

Use a separate, clearly named test database with `RAW` and `CURATED` schemas and the same table definitions. Build a **test-only copy** of the procedure bundle and SQL with a checked, exact replacement of the `QUAKEWATCH.` database qualifier; leave the production files unchanged. The test copy must use its own internal stage and procedure. The offline [namespace validator](../scripts/phase2_fixture_namespace.py) enumerates fully qualified object references in every procedure module and required DDL file, rejects unknown databases or schemas, and checks that no source database qualifier survives the rewrite. Run `PYTHONPATH=src:. .venv/bin/python scripts/phase2_fixture_namespace.py`; this does not connect or create a bundle. Recheck the account's supported Python runtime and Snowpark package before deploying the copied procedure.

Build the test-only import ZIP and SQL files with `PYTHONPATH=src:. .venv/bin/python scripts/build_phase2_fixture_bundle.py`. The builder validates every source before writing to ignored `data/procedure/phase2_fixture/`, then inspects the generated ZIP and SQL for production references. This local artifact build does not deploy anything.

The proposed account setup is [phase2_fixture_setup.sql](../sql/phase2_fixture_setup.sql). It creates a new database, `RAW` and `CURATED` schemas, and grants only the existing `QUAKEWATCH_ROLE` the object-creation privileges needed there. It deliberately has no `IF NOT EXISTS`: if the name is already occupied, setup must stop for inspection. The later test stage and tables would be created by the project role, in a separate step. This SQL is prepared only; no database has been created. A live setup would require a preflight of the target name and owner approval for the account change and possible charges.

Preview the [name preflight](../scripts/phase2_fixture_name_check.py) with `PYTHONPATH=src:. .venv/bin/python scripts/phase2_fixture_name_check.py`. Its approved `--execute` mode used the existing `quakewatch_admin` profile for one metadata-only `SHOW DATABASES LIKE` query; it filters the result to an exact name because SQL `LIKE` treats underscores as wildcards. It does not create or alter an account object, and it never prints the profile password. On 2026-09-30, this check reported `Fixture database name: available for setup review`. Recheck immediately before creation because availability can change.

The guarded [setup runner](../scripts/phase2_fixture_setup.py) previews the 12 reviewed statements with `PYTHONPATH=src:. .venv/bin/python scripts/phase2_fixture_setup.py`. Its `--execute` mode rechecks the exact name on the same admin connection immediately before running SQL, rejects any edit to the reviewed statement list, and verifies database and schema visibility afterward. A failure after `CREATE DATABASE` can leave partial fixture setup; inspect it before any retry. The live mode has not run and requires separate approval for the account change and possible cloud services/storage charges.

Load only the three documented same-event source fixtures into separate test RAW attempts with explicit synthetic manifests and complete count receipts. Process original, later revision, and tombstone in that order, then replay the original as a fourth attempt. After each call, check the revision fact, current view, processing audit, and duplicate grain keys. Expected current state: original active, later magnitude `1.28`, absent after deletion, still absent after stale replay. Preserve all historical revision rows and report rejects. A further overlapping rerun should merge zero new revisions.

This test database and its staged files would persist until deliberately cleaned up. Creating it, loading it, running the warehouse, and later deleting it each require a separate review of cost and data effects. No command in this plan authorizes those actions. The plan does not change the frozen core architecture: production still reads USGS batch data through the existing RAW and Snowpark path. This fixture proves model behavior on synthetic inputs only, not that the catalog-wide update sweep captured every real old-event change.
